## 7. 必测验收矩阵

| 场景 | 应有结果 |
|---|---|
| 新档与旧档副本加载 | 内容正常出现，既有数据不被整表覆盖，必要原料和解锁都有正常来源 |
| 多原料不足 | 不扣任何材料，不启动机器 |
| 跨品质、多个物品堆叠 | 按已记录的消耗规则正确扣除所需总量，不重复计算 |
| 机器忙、重复点击、重复请求 | 不改配方、不再次扣料、不多产出 |
| 开工、完成、领取后的存读档 | 时间与状态连续；已经领取的批次不会再次生成 |
| 领取时背包满 | 产品仍可领取，不消失、不复制 |
| 跨日、季节切换 | 已开工批次继续按规则完成；作物与采集按设定季节生效 |
| 两名玩家争用同一设备 | 主机只接受一次有效事务，双方状态一致 |
| 空闲和工作状态搬动设备 | 空闲可移动；加工中与待领取时阻止搬动，物品不丢失 |
| 原版熏鱼与新增熏制 | 原版鱼类、原版耗材及两个新配方均按各自规则运行 |
| 全部配方及商店解锁 | 不靠控制台，无断链原料、缺失菜谱或不可获取设备 |
| 采集点竞争 | 新采集物可获得，原版关键采集物仍保有可获得性 |
| 分类、职业与完成度 | 实际结果与发布说明一致，没有未经评估的收益或完成度影响 |

## 8. 风险与处理顺序

| 风险 | 处理方式 |
|---|---|
| 同原料多产物与多输入无法只靠常规数据交互承载 | P1 优先验证共享代码模块；不拆成多台单用途设备 |
| 联机重复扣料或重复领取 | 先完成主机确认、状态同步与并发操作验证，再扩大内容 |
| 新熏制规则影响原版加工 | 追加特定配方，并以原版鱼类流程作回归检查 |
| 季节原料不足造成料理长期不可做 | 按设计提供有限季外补货，调整供给数值而非加新原料体系 |
| 内容增加导致制作成本失控 | 按冻结清单逐项交付，排除项不进入开发待办 |

先完成 P0，再依次推进 P1、P2、P3。当前不承诺未经原型验证的开发工期。
