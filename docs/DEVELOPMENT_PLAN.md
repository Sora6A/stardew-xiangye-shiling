# 《乡野时令》开发计划

日期：2026-09-22  
对应设计：[0.4 收敛版](DESIGN.md)  
当前状态：仅完成设计与任务拆解。以下实现与游戏内验收均未执行。

## 1. 交付目标与边界

交付一个具有完整获取、生产和使用路径的模组。玩家能采集四种春季野菜、种黄豆和大白菜，用豆坊、发酵缸、原版熏鱼机与厨房制作设计文档中列出的食品。

| 范围指标 | 固定数量 | 说明 |
|---|---:|---|
| 新原料 | 8 | 4 种采集物、2 种作物、2 种商店食材 |
| 加工品 | 15 | 6 种基础豆制品、3 种豆制熟食、4 种发酵品、2 种烟熏品 |
| 配套料理 | 13 | 不由菜名反向增加原料或机器 |
| 新食品物品合计 | 36 | 原料、加工品与料理；种子和设备另计 |
| 新种子 | 2 | 黄豆种子、大白菜种子 |
| 新设备 | 2 | 豆坊、发酵缸 |
| 豆坊配方 | 6 | 直接选择产品，不强制串接背包中间物 |
| 发酵缸配方 | 4 | 酱油、黄豆酱、川式豆瓣、酸菜 |
| 熏鱼机新增配方 | 2 | 猪肉→腊肉；豆干→熏豆干 |
| 厨房新增食品配方 | 16 | 13 道料理＋素鸡、油豆腐、兰花干 |

数量、工时、售价、恢复量和解锁价格在原型中调整；物品品种、来源路线和设备数量以设计文档为准。新增分支必须先修改范围基线，不能作为实现时的顺手扩展。

- [ ] 建立内容包与最小代码模块的目录、构建方式和加载说明。
- [ ] 确定独立 ID 命名空间，为 36 种食品物品、2 种种子、2 种设备及其配方建立清单。
- [ ] 为每项记录来源、使用去向、类别、显示名称、图像、本地化键和解锁方式；标出尚待平衡的数值。
- [ ] 明确数据补丁与代码边界：常规物品、作物、商店、菜谱与美术由数据承载；两种设备共享交互，只增加必要代码。
- [ ] 准备新档、旧档副本与双人联机验证环境。

## 4. P1：先验证公共机制

依赖：P0 完成。用两条最短流程证明设计可实现，再填充内容。

原型流程：

- 黄豆→豆坊→豆腐；香椿＋豆腐→厨房→香椿拌豆腐。
- 黄豆＋小麦→发酵缸→酱油。

任务：

- [ ] 实现豆坊、发酵缸共享的简单配方菜单，显示解锁状态、原料数量、产量和预计完成时间。
- [ ] 首轮正式支持从玩家背包投料；不额外增加箱子联动或自动化系统。
- [ ] 采用“空闲→加工→待领取→空闲”的状态流转；加工中与待领取时均不能换配方。
- [ ] 校验全部输入后一次提交扣料与开工；原料不足、请求重复或机器忙时不得部分扣料。
- [ ] 固定本批次配方、投入、产出数量和结束时间；保存并恢复进行中的工作。
- [ ] 背包空间不足时保持产品待领取，完整领取成功后才清空机器，避免吞物或重复领取。
- [ ] 由主机确认开工与领取，同步机器状态；验证两名玩家同时操作一台机器。
- [ ] 明确机器移动规则：加工与待领取期间阻止搬动；空闲时按正常放置设备处理，并验证存读档。
- [ ] 将两条原型流程接入正常获取途径：商店或采集提供原料，罗宾提供设备图纸，格斯提供食品配方。

交付物：可在游戏内完整走通的两条流程与共享设备模块。  
完成条件：不用控制台也能从获取原料走到使用成品；缺料、满包、存读档和双人竞争均不丢料、不复制产物。P1 不通过时，先修公共机制，不扩充食品数量。

## 5. P2：填齐冻结范围

依赖：P1 的公共机制通过验收。按清单复用机制，不追加专用工具。

| 工作包 | 实现内容 | 完成条件 |
|---|---|---|

| 豆坊 | 豆浆、豆花、豆腐、油豆皮、千张、豆干 | 六个选择各有明确消耗、产量和时间，均能完成与领取 |
| 发酵缸 | 酱油、黄豆酱、川式豆瓣、酸菜 | 四个配方有效；酱油消耗黄豆与小麦，川式豆瓣消耗蚕豆与辣椒 |
| 熏鱼机 | 腊肉、熏豆干 | 两个新增配方有效；燃料规则明确；原版鱼类加工回归通过 |
| 厨房 | 三种豆制熟食、十三道料理 | 共十六个配方可学习、可制作；所有原料都有正式来源 |

| 美术与文案 | 物品、种子、作物、设备图像及本地化文本 | 图标、作物阶段和设备状态完整；内部 ID 不依赖显示名称 |

完成条件：逐项记录“来源→加工或烹饪→食用、送礼或继续加工”的验证结果；食物可以作为终点，不为了凑用途再加菜。

## 6. P3：平衡、兼容性验证与发布准备

依赖：P2 内容齐全。

任务：

- [ ] 建立经济核算表：原料成本、机器占用时间、每批数量、出售所得、恢复量和解锁成本。
- [ ] 检查原料直售、基础豆制品、发酵调味品与料理的价值，避免一种配方长期压倒其他选择。
- [ ] 核对酱油、黄豆酱和川式豆瓣的小份批量产出与菜谱消耗，使调味品足够使用且收益合理。
- [ ] 完成物品分类、职业加成、赠礼、收集页面与完成度规则，并在说明中记录实际行为。
- [ ] 完成下方验收矩阵；仅声明实际测过的游戏、平台和模组组合。
- [ ] 检查所有图像在背包、地面、商店、菜单和机器状态中的显示。
- [ ] 编写安装、更新、配置与故障反馈说明；更新保持 ID 稳定，卸载说明包含备份与处理模组物品。
- [ ] 清理临时素材、调试入口和开发文件，核对素材来源及发布许可后制作发行包。
- [ ] 在干净的目标环境安装发行包并完成一次正常游玩流程，再标记首个可玩版本。

交付物：平衡记录、验收结果、用户说明和可安装发行包。  
完成条件：全部必测项通过或明确修复；不把设计版本号当作已发布代码版本；不对未测的地图扩展、Automate 等作兼容保证。

## 7. 必测验收矩阵

| 场景 | 应有结果 |
|---|---|
| 新档与旧档副本加载 | 内容正常出现，既有数据不被整表覆盖，必要原料和解锁都有正常来源 |
| 多原料不足 | 不扣任何材料，不启动机器 |
| 跨品质、多个物品堆叠 | 按已记录的消耗规则正确扣除所需总量，不重复计算 |
| 机器忙、重复点击、重复请求 | 不改配方、不再次扣料、不多产出 |
| 开工、完成、领取后的存读档 | 时间与状态连续；已经领取的批次不会再次生成 |
| 领取时背包满 | 产品仍可领取，不消失、不复制 |
| 跨日、季节切换 | 已开工批次继续按规则完成；作物与采集按设定季节生效 |
| 两名玩家争用同一设备 | 主机只接受一次有效事务，双方状态一致 |
| 空闲和工作状态搬动设备 | 空闲可移动；加工中与待领取时阻止搬动，物品不丢失 |
| 原版熏鱼与新增熏制 | 原版鱼类、原版耗材及两个新配方均按各自规则运行 |
| 全部配方及商店解锁 | 不靠控制台，无断链原料、缺失菜谱或不可获取设备 |
| 采集点竞争 | 新采集物可获得，原版关键采集物仍保有可获得性 |
| 分类、职业与完成度 | 实际结果与发布说明一致，没有未经评估的收益或完成度影响 |

## 8. 风险与处理顺序

| 风险 | 处理方式 |
|---|---|
| 同原料多产物与多输入无法只靠常规数据交互承载 | P1 优先验证共享代码模块；不拆成多台单用途设备 |
| 联机重复扣料或重复领取 | 先完成主机确认、状态同步与并发操作验证，再扩大内容 |
| 新熏制规则影响原版加工 | 追加特定配方，并以原版鱼类流程作回归检查 |
| 季节原料不足造成料理长期不可做 | 按设计提供有限季外补货，调整供给数值而非加新原料体系 |
| 内容增加导致制作成本失控 | 按冻结清单逐项交付，排除项不进入开发待办 |

先完成 P0，再依次推进 P1、P2、P3。当前不承诺未经原型验证的开发工期。
